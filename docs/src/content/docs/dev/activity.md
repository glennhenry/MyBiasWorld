An activity records and documents a particular event that happened within the platform. It can be produced through user actions or generated by the system based on certain conditions. Activities are produced to preserve the turn of events that occured in the platform.

:::note
Activities are not server log. While server log describe the system condition or flow of services and is intended to be read by developer or server administrators, activities are rather log of events in the fan social portal domain.

Server log of system should use the Fancam track event instead.
:::

### Model

An activity is modeled as an object that describes the details of the activity. Each activity has:

- A source telling where the activity was produced.
- A type which is the context detail of the activity.
- A record of the timestamp of when the activity happened
- Metadata fields containing arbitrary data for the activity.

For example, a user liking a topic in the cafe may generate the following activity:

```json
{
  "source": "ActivitySource.Cafe",
  "type": "CafeActivity.TopicLiked",
  "timestamp": 1788519104768,
  "metadata": {
    "likedBy": "d8fbe779-03a7-43ba-b752-cd89f62d465b",
    "topicId": "ce913ba2-cacc-416e-a67e-e3ccb623bd89",
    "topicAuthorId": "41c31087-caf9-40fa-b893-24e9ff501f2e",
    "likesAmountNow": 23
  }
}
```

A user registering an account can be framed as "a user joining the platform," and may generate the following activity:

```json
{
  "source": "ActivitySource.Users",
  "type": "UsersActivity.UsersJoined",
  "timestamp": 1788519104768,
  "metadata": {
    "userId": "d8fbe779-03a7-43ba-b752-cd89f62d465b",
    "username": "kep1ian001",
    "countryOrigin": "Indonesia"
  }
}
```

Design principles:

- Activity is a record of action — it should only contain details of the action.
- The model shouldn't be overengineered with special type system or inheritance. It should be simple with enum for activity source, freeform string for type, and arbitrary fields on metadata.
- The type follows the format of title case and is separated by dot. It describes the context of the activity.

### Pub-Sub

Activity system is implemented with pub-sub system. Server component reacts to a certain circumstance and produce an activity model. Another component can opt-in to receive that type of events for its own need.

Components of server can call a class like `ActivitySubunit` to emit the activity, while `ActivityReceiver` is an interface that can be inherited to register to specific event source or type and handle them when they are fired.

### Source

Based on how an activity can be produced, there are 2 modes:

1. By users activity: The majority of activity is intended to the capture the "activity" of the platform. It can be produced directly by network handlers from users activity. Users activity includes any phenomenon that is performed by the user such as topic creation, topic likes, reply written, comment written, user reach level, user earn badges, and many more.
2. Activity conditions: This is an update to tell users about the surrounding environment of the platform. It isn't prompted directly by user, but rather invoked after a certain condition is fulfilled (which may work similarly as above but with extra steps). It may include an update of cafe posts (e.g., views, likes, or replies reach a high amount) or an update of the platform activities (e.g., 9 people playing billiard, 12 users just registered today).

### Output

There are 4 ways to utilize the static record of activity:

1. Activity feed: Through a class like `ActivityFeedSubunit`, activity model can be transformed into a textual output intended to be read by users in the portal lobby. It consumes a raw model of activity, translate it, then produce an ambienced model.
2. User's activity history: Through a class like `UserActivitySubunit`, activity model can be transformed into another model of user activity history. It is intended to be saved in the user's history data. Every activity of an individual user is recorded as a history, but not every activity may be broadcasted to the activity feed.
3. [Radio](/docs/radio): The radio is a small, active announcement system that appears on every page of the site. Since the user won't be on the portal lobby all the time, the radio can be used to keep up the users with activity updates.
4. Activity log file: It has the similar purpose with event log of system. It produces a log file containing the list of activities that happened in the platform. The log file contains the raw data model of activities which may be in the format of JSONL. It serve a purpose for an archive and may be read by system administrators or parsed by machine to be visualized or analyzed.

### Translation

Activity can be utilized to add liveliness to the platform by turning the static log data into a textual model to be read by users.

For example:

- "User kep1ian001 has reached level 5!" (user level up activity)
- "User kep1ian002 has earned 'WA DA DA' badge" (user earn badge activity)
- "User kep1ian003 liked your 'Favorite song?' post" (cafe like activity)
- "Post 'Favorite song?' has earned 30 likes in under an hour" (cafe condition evaluation activity)
- "30 people are currently playing billiard" (game environment evaluation activity)
- "903 people have earned the 'WA DA DA' badge" (user badges evaluation activity)

Since activity model is kept to data only, there has to be a component that transforms the raw model into the textual human output. We call this component as the `ActivityTranslator`. This component is crucial to decouple between the static activity data with the various output model.

A single activity data describing that user A liked the post of user B should be transformable to both:

- "User A has liked your post" (user POV)
- "User A liked post X made by User B" (third-person POV)

#### Translation file

Translator shouldn't list every possible translation in the code, but rather it should be taken from an external file (e.g., JSON).

The translator is simply:

- Load the corresponding strings translation file. The file contains a list of text format like `"Cafe.Post.LikeReachedAmount": "Post '{postTitle}' has reached '{amountOfLikes}' likes."`. Differnt POV of the translation should be separated to a different string file.
- Serve translation functionality directly by a lookup to the strings file or behave differently based on metadata. A special metadata like `hyperlink: "/xyz"` may generate a hyperlink text instead of a plain text output.
