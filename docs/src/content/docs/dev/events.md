Events include various kinds of activities and actions that happened within the platform. They can be produced by user actions or generated by the system based on certain conditions. The purpose of events is to add ambience and to broadcast the surrounding activities within the platform.

:::note
Events are not server log. While server log describe the system condition and is intended to be read by developer or server administrators, events are rather log of activities that happened within the platform.

A server log could be "Successfully registered userId=XYZ", but an event frame it like "User [display name] has registered. Welcome!".
:::

### Model

An event is modeled as an object that describes the details of the event. Each event has:

- A type, the high-level description that classifies events.
- A subtype, the sub-level description within each classification.
- A record of the timestamp of when the event happened
- Metadata fields containing arbitrary data for the event.

For example, a topic liked by other user may generate the following event:

```json
{
  "type": "EventType.Cafe",
  "subtype": "CafeEvent.TopicLiked",
  "timestamp": 1788519104768,
  "metadata": {
    "likedBy": "d8fbe779-03a7-43ba-b752-cd89f62d465b",
    "topicId": "ce913ba2-cacc-416e-a67e-e3ccb623bd89",
    "topicAuthorId": "41c31087-caf9-40fa-b893-24e9ff501f2e",
    "likesAmountNow": 23
  }
}
```

- Each event should only contain data and not interpretation. This decouples between event producers and event broadcaster.
- The model shouldn't be overengineered with special type system or inheritance. Make it simple by utilizing string for event type and arbitrary fields on metadata.

### Source

Any components in the server should be able to produce events through a class like `EventService`.

Based on how an event can be produced, there are 2 sources:

1. By users activity: The majority of events is intended to the capture the liveliness of the platform. This source of event is produced directly by network handlers from users activity. Users activity includes topic created, topic liked, reply written, comment written, user reach level, user earn badges, and many more.
   - "User kep1ian001 has reached level 5!"
   - "User kep1ian002 has earned 'WA DA DA' badge"
   - "User kep1ian003 liked your 'Favorite song?' post"
2. Activity conditions: This is an update to tell users about the surrounding environment of the platform. It isn't prompted by an activity, but rather invoked after a certain condition is fulfilled (which may work through network handlers but with extra steps). It may include an update of cafe posts (e.g., views, likes, or replies reach a high amount) or an update of the platform activities (e.g., 9 people playing billiard, 12 users just registered today).
   - "Post 'Favorite song?' has earned 30 likes in under an hour"
   - "30 people are currently playing billiard"
   - "903 people have earned the 'WA DA DA' badge"

### Output

The static data model of event is consumed by event broadcaster. There are 4 output model of event:

1. Activity feed: Through a class like `ActivityFeedService`, this model produces a textual output intended to be read by users in the portal lobby. It consumes raw model of event, interprets it, then produce an ambienced model.
2. User's activity history: Through a class like `UserActivityService`, this model transforms a raw event model into another model of activity history. It is intended to be saved in user's history data. Every event of individual user activity will be recorded as a history, but not every event may be broadcasted to the activity feed.
3. [Radio](/docs/radio): The radio is a small, active announcement system that appears on every page of the site. Since the user won't be on the portal lobby all the time, the radio can be used to keep up the users with activity updates.
4. Event log file: This output model produces a log file containing the list of events that happened after some period of time. The log file contains the raw data model of events which may be in the format of JSONL. It serve a purpose for an archive and may be read by system administrators or parsed by machine to be visualized or analyzed.

#### Interpretation

The dependence of various output model with event interpreter that produces textual form for human should be decoupled.

`ActivityFeedService` or `UserActivityService` should depend on class like `UserEventInterpreter` to generate text output. Likewise, the event intended to be broadcasted on the radio may depend on the same class.

The interpreter shouldn't list every possible interpretation in the code, but rather it should be taken from an external file (e.g., JSON).

The interpreter works by:

- Load the corresponding strings interpret file. The file contains a list of text format like `"Cafe.Post.LikeReachedAmount": "Post '{postTitle}' has reached '{amountOfLikes}' likes."`
- Serve interpretation functionality by requiring a specific target output or behave differently based on metadata. For example, the input event could be `Event.Cafe` with subtype of `CafeEvent.TopicLiked`, but `ActivityFeedService` uses an output of `InterpretOutput.Feed`, whereas `UserActivityService` (through a different activity model) uses an output of `InterpretOutput.Self`. A special metadata like `hyperlink: "/xyz"` may generate a hyperlink text instead of a plain text output.

### Architecture

The event system can make use of pub-sub architecture where event producer can simply produce events like `EventService.event(...)` and event consumers subscribe to a particular type of events.

Consumer like `UserActivityService` may subscribe to events with the type of users activity. The class may directly save every events as an activity model to the database. Whereas, a consumer like `NotableActivityService` may subscribe to a specific type of events only and enforcing constraints before actually outputting the event.

For example, the `LikePostHandler` produce an event of `Event.Cafe` with subtype of `CafeEvent.TopicLiked`. The `NotableActivityService` receives this event and check if the amount of likes exceed a high amount of 100. If so is true, it will call the `RadioService` to output the event as a radio broadcast.
